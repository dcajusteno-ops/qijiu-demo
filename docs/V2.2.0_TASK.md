## 1. 版本背景

`Comfy Manager` 当前稳定版本为 `v2.1.6`，已经具备以下核心能力：

- 绑定任意 `ComfyUI output` 目录
- 图库浏览、搜索、分页、排序
- 标签、笔记、收藏夹、收藏分组
- 日期产出工作台
- 模型 / LoRA 筛选
- 自动规则引擎
- Prompt 助手
- 图片详情 `Lightbox`
- 批量操作、A/B 对比、图片堆叠
- 统计面板、回收站、工具菜单、设置中心

项目已经完成“功能闭环”的第一阶段，`v2.2.0` 不适合继续无节制叠加新页面，而应优先处理一个会影响长期使用体验的核心问题：

- 图库规模变大后，首屏进入、切换目录、筛选、滚动和批量操作的流畅度会逐步下降

因此，`v2.2.0` 当前正式纳入以下 `7` 个任务：

- `大型图库性能模式`
- `创作批次管理`
- `批量重命名与命名规则`
- `导出包助手`
- `目录健康中心`
- `模型 / LoRA 资产档案`
- `精选集 / 展示板`

## 2. 本次结论先说清

### 2.1 v2.2.0 当前是否只保留一个任务

结论：**不再只保留一个任务**。

当前版本任务书已经正式收录 `7` 个任务，但仍然要区分优先级：

- `P0`：大型图库性能模式
- `P1`：目录健康中心、创作批次管理、导出包助手
- `P2`：批量重命名与命名规则、模型 / LoRA 资产档案、精选集 / 展示板

原因：

- 性能模式决定底层承载能力
- 目录健康、导出、批次管理与现有工作流结合最紧
- 其余任务适合在性能链路稳定后逐步接入

### 2.2 本版本的主线是什么

结论：`v2.2.0` 的主线仍然是把现有图库系统升级成可承载更大规模图片资产的稳定工作台，并在此基础上补齐“批次、导出、治理、资产管理、展示”五条产品能力线。

### 2.3 本次任务书的定位

这份任务书用于定义：

- `7` 个正式任务的产品目标
- 各任务的范围、边界、优先级与依赖关系
- 后端扫描 / 缓存 / 分页 / 预览链路的优化方向
- 前端状态层、列表渲染和新页面入口的收敛方案
- 阶段拆解、验收标准、风险边界

## 3. 当前现状与问题判断

结合当前实现，可以初步确认以下性能特征：

### 3.1 后端现状

主文件：

- `desktop-source/app.go`

当前 `GetImages(sortBy, sortOrder)` 的主要特点：

- 每次读取图片列表时，都会遍历受管目录
- 会为当前遍历结果构建新的图片列表
- 会维护并刷新 `image-meta-cache.json`
- 会在返回结果后触发 metadata warmup
- 当前返回结果仍然是“全量图片数组”

这意味着，当图片总量持续上升时，以下成本会同步上升：

- 目录遍历成本
- 图片列表组装成本
- 元数据缓存比对成本
- 前端接收和持有大数组的成本

### 3.2 前端现状

核心状态文件：

- `desktop-source/frontend/src/composables/useImages.js`

当前状态链路特点：

- 前端会持有全量图片列表
- 目录树、筛选项、结果集、分页数据主要在前端派生
- 搜索、标签、模型、LoRA、日期工作台等过滤会叠加到同一份大列表上
- 图片分页是“拿到完整结果后再分页”

这意味着：

- 数据量越大，前端响应式更新成本越高
- 某些筛选切换会带动较大的派生计算
- 进入图库时，即使用户只看前 `50` 张，也会先拿到完整集合

### 3.3 列表渲染现状

相关文件：

- `desktop-source/frontend/src/components/ImageGallery.vue`
- `desktop-source/frontend/src/components/ImageCard.vue`

当前特点：

- 已有分页
- 已有批量模式
- 已有 A/B 对比
- 已有图片堆叠

但在大图库下仍然存在潜在问题：

- 首次进入前仍依赖完整数据准备
- 图片卡片数量较大时，渲染和状态更新成本会明显增高
- 筛选变化会反复驱动整组卡片更新

### 3.4 现有基础并不差

当前项目已经有一些可复用的性能基础设施：

- `image-meta-cache.json`
- metadata warmup 机制
- `data/image-variants/preview`
- `data/image-variants/thumb`
- `ClearPreviewCache()`
- 图片堆叠能力

结论：`v2.2.0` 不需要推翻现有结构，而应在现有缓存、预览、分页基础上做“分层升级”。

## 4. 版本目标

### 4.1 核心目标

让 `Comfy Manager` 在大型图库场景下仍然保持：

- 可进入
- 可筛选
- 可滚动
- 可定位
- 可批量操作
- 可持续使用

### 4.2 对“大型图库”的定义

本版本建议先按以下量级定义性能模式触发场景：

- `3000+` 张图片：开始进入中大型图库
- `10000+` 张图片：进入大型图库
- `30000+` 张图片：进入超大型图库

说明：

- 这不是硬编码限制
- 只是用于制定默认策略和验收目标

### 4.3 用户视角的版本承诺

用户不需要理解底层缓存和索引细节，只需要明确感知到：

- 首次进入图库不再“整页发呆”
- 切换筛选不再频繁卡顿
- 滚动浏览更稳定
- 软件会主动告诉用户当前是否处于性能模式
- 用户可以在性能与信息密度之间做合理取舍

## 5. 功能名称与定义

### 5.1 功能名称

`大型图库性能模式`

### 5.2 功能说明

大型图库性能模式是一套面向大规模图片资产的性能收敛方案，不是单一按钮，也不是单一优化点。

它应同时覆盖：

- 数据获取策略
- 缓存策略
- 列表渲染策略
- 预览图策略
- 元数据读取策略
- 用户反馈与切换策略

### 5.3 目标效果

当图库规模较大时，系统自动或手动进入“性能优先”的工作模式，并采用更保守、更轻量的资源策略，以换取稳定的浏览和整理体验。

## 6. 设计原则

本节结合当前项目风格和 `$ui-ux-pro-max` 技能建议，明确本次功能的设计方向。

### 6.1 视觉方向

本次功能 UI 应继续保持：

- 简约风
- 工具型
- 状态清楚
- 反馈明确

不建议把“性能模式”做成夸张、情绪化、带强烈营销感的视觉模块。

### 6.2 交互原则

性能模式的交互要求：

- 让用户知道系统正在做什么
- 对等待超过 `300ms` 的操作给出反馈
- 尽量用骨架屏、分段加载和轻量进度，而不是整页阻塞
- 不让用户面对“白屏 + 无提示 + 不知道是否卡死”

### 6.3 组件层原则

根据技能建议，本次前端实现可优先考虑：

- 大列表状态使用更轻量的响应式策略
- 对昂贵列表项减少不必要重渲染
- 对图片卡片和派生结果采用更明确的 memo / 缓存边界
- 对大对象状态评估 `shallowRef` 等更保守策略

### 6.4 本次不追求的方向

本次不以“炫技 UI”为目标，不做：

- 华丽大屏式性能中心
- 高饱和性能仪表盘
- 复杂动画演出
- 大面积渐变或强装饰提示条

## 7. 用户可见能力定义

### 7.1 性能模式状态感知

建议增加明确的用户感知能力：

- 当前是否处于性能模式
- 为什么进入性能模式
- 当前采用了哪些性能策略
- 用户是否可以手动切换

推荐落点：

- `SettingsCenterDialog.vue`
- 图库页顶部轻量状态条

### 7.2 模式切换方式

建议提供三种模式：

- `自动`
- `标准`
- `性能优先`

定义建议：

- `自动`：根据图库规模、目录规模、设备表现自动决定
- `标准`：优先保留完整信息和现有体验
- `性能优先`：优先保证速度和稳定性

### 7.3 性能优先模式下建议启用的策略

建议至少包含以下策略：

- 优先使用缩略图 / 预览图，而不是直接读取原图
- 首屏只加载首批结果
- 元数据按需加载
- 减少一次性渲染的卡片数
- 对非可视区域延迟加载
- 降低部分统计和派生计算的实时性

### 7.4 用户可控项

建议允许用户单独控制以下选项：

- 是否自动启用性能模式
- 首屏加载数量
- 每页默认数量
- 是否优先显示缩略图
- 是否后台预生成缩略图
- 是否在图库页立即显示完整元数据

## 9. 建议的能力拆解

### 9.1 第一层：首屏可进入

目标：

- 进入图库页时，优先让用户尽快看到第一批可浏览内容

建议措施：

- 首批结果优先返回
- 预览图优先
- 非关键元数据延迟读取
- 骨架卡片即时占位

### 9.2 第二层：滚动和翻页稳定

目标：

- 用户浏览列表时，不因为长列表和大图解码导致明显掉帧

建议措施：

- 列表虚拟化或分段挂载
- 图片进入视区后再加载
- 降低同时在 DOM 中存活的卡片数量

### 9.3 第三层：筛选切换更轻

目标：

- 搜索、标签、模型、LoRA、日期筛选切换时，不要对全量大数组反复做重计算

建议措施：

- 前后端职责重新划分
- 对高频筛选结果做缓存
- 降低不必要的深层响应式依赖

### 9.4 第四层：后台慢慢补齐细节

目标：

- 用户先能工作，再逐步拿到完整信息

建议措施：

- 缩略图后台生成
- metadata warmup 继续保留
- 统计卡片在后台更新
- 需要时再展示“正在补全更多信息”

## 10. 技术方向建议

### 10.1 后端方向

建议优先评估以下优化：

- 为图片列表增加“轻量结果”与“完整结果”的区分
- 为列表读取增加分页 / 分段返回能力
- 为目录扫描增加更稳定的缓存复用策略
- 缩略图 / 预览图生成链路正式接入主流程
- 将部分聚合数据提前落入缓存，而不是每次临时现算

建议新增或重构的能力方向：

- `GetImagesPage(query)`
- `GetImageGallerySummary()`
- `EnsureImageVariant(relPath, kind)`
- `GetPerformanceModeSettings()`
- `SavePerformanceModeSettings(settings)`

说明：

- 这里是接口方向，不要求接口名最终完全一致

### 10.2 前端方向

建议优先处理以下问题：

- `useImages.js` 对全量图片数组的重依赖
- 目录树、筛选项、分页结果统一依赖全量数组
- 大列表渲染时卡片反复重算

建议方向：

- 把“当前页数据”和“完整结果集”解耦
- 大对象状态评估使用更轻的响应式容器
- 对图片卡片启用更明确的渲染边界
- 对派生结果做缓存和分段计算
- 评估列表虚拟化方案

### 10.3 缩略图与预览图方向

当前项目已经有：

- `data/image-variants/preview`
- `data/image-variants/thumb`

`v2.2.0` 应明确它们的职责：

- `thumb`：列表级浏览优先使用
- `preview`：Lightbox 或中尺寸预览优先使用

建议原则：

- 图库卡片默认不直接依赖原图尺寸解码
- 原图只在真正需要时再读取

### 10.4 统计与工作台方向

建议在性能模式下，对以下模块采用轻量策略：

- 工作台统计
- 时间线统计
- 模型 / LoRA 聚合统计
- 目录树图片数

建议：

- 先显示最近缓存值
- 后台再静默刷新
- 避免每次视图切换都同步重算

## 15. 风险与注意事项

### 15.1 主要风险

- 如果只优化渲染，不优化数据链路，效果会有限
- 如果只优化后端，不优化前端状态层，卡顿仍然会存在
- 如果性能模式影响现有交互一致性，用户会困惑
- 如果缩略图生成策略不稳，可能出现缓存膨胀或旧图残留

### 15.2 开发注意点

- 不要为了性能直接删掉现有信息能力
- 优先采用“延迟展示”而不是“永久缺失”
- 不要让性能模式破坏现有路径与缓存安全边界
- 要确保标准模式仍然可用

### 15.3 一条很重要的原则

性能模式不是“低配模式”或“残缺模式”，而是“更保守的资源分配策略”。

## 17. 正式任务二：创作批次管理

### 17.1 任务目标

把同一轮出图结果归为一个“批次”或“会话”，让用户能围绕一次创作过程回看、筛选、归档，而不是只能按目录或日期查看。

### 17.2 适合解决的问题

- 同一天存在多个主题或多轮实验，日期维度不够细
- 同一批图片分散在不同目录，回看成本高
- 用户需要为一轮创作补备注和上下文

### 17.3 建议范围

- 新增批次实体：`batchId / name / note / createdAt / updatedAt`
- 图片支持关联到批次
- 图库支持按批次浏览
- 支持从当前筛选结果创建批次
- 支持批次重命名、备注、删除、移除成员

### 17.4 本次不做

- 多层批次嵌套
- 云同步协作
- 自动按 prompt 智能推断批次

### 17.5 建议数据方向

- `data/batches.json`
- `data/image-batches.json`

### 17.6 验收标准

- 用户可创建批次并将图片加入批次
- 用户可按批次打开图片集合
- 批次备注可持久化
- 删除批次不会删除原图

### 17.7 任务定位收敛

`创作批次管理` 的目标不是再做一套复杂项目管理系统，而是补一层比“日期目录”更贴近真实创作过程的组织方式。

首版目标收敛为：

1. 让用户可以把同一轮出图结果归为一个批次
2. 让批次能被浏览、重命名、补备注、移除成员
3. 让批次与现有图库、Lightbox、批量模式自然联动

首版不追求：

- 多层批次嵌套
- 批次模板系统
- 自动智能分批
- 跨用户协作

## 18. 正式任务三：批量重命名与命名规则

### 18.1 任务目标

为批量模式补齐命名管理能力，让用户在导出、精选、归档之前能先整理文件名。

### 18.2 适合解决的问题

- 默认文件名不具备可读性
- 导出后的资料难以长期归档
- 同一主题图片命名缺乏一致性

### 18.3 建议范围

- 支持对选中图片批量重命名
- 支持命名模板
- 支持重命名结果预览
- 支持冲突检测
- 支持执行前确认

### 18.4 建议模板变量

- `{date}`
- `{time}`
- `{model}`
- `{batch}`
- `{tag}`
- `{index}`
- `{name}`

### 18.5 本次不做

- 正则脚本式高级重命名
- 跨目录复杂重排
- 历史版本无限回滚

### 18.6 验收标准

- 用户可以看到批量重命名预览
- 命名冲突会被阻止或自动处理
- 重命名后标签、收藏、笔记、批次引用不丢失

### 18.7 任务定位收敛

`批量重命名与命名规则` 的目标不是做通用文件管理器级别的重命名脚本系统，而是补齐当前图库整理链路中最缺的一环：

- 让图片在导出、归档、精选前具备一致且可读的文件名

首版目标收敛为：

1. 支持对选中图片批量重命名
2. 支持少量高频模板变量
3. 支持执行前预览结果和冲突检测
4. 确保重命名后项目内引用保持一致

首版不追求：

- 正则表达式脚本化重命名
- 可编程规则引擎
- 复杂多阶段回滚系统
- 跨目录批量重排

### 18.8 当前基础与实现方向

当前项目已经有：

- `moveManagedImageToFolder(...)`
- `remapManagedImageReferences(oldRelPath, newRelPath)`
- `BatchMove(...)`

这说明项目已经具备：

- 单图路径变化后的引用更新能力
- 标签、笔记、收藏分组、元数据缓存的路径重映射逻辑

因此，`批量重命名` 的正确实现方向不是重复写一套引用同步逻辑，而是：

- 在现有 `remapManagedImageReferences(...)` 基础上扩展
- 将“改文件名”视作“同目录内路径变更”

### 18.9 数据结构草案

首版建议不单独为“重命名规则”建立持久化文件。

原因：

- 首版先做即时重命名
- 用户输入模板后直接生成预览并执行
- 没必要提前引入规则存档、规则库、规则历史

建议新增结构：

```ts

  | 'date'
  | 'time'
  | 'model'
  | 'batch'
  | 'tag'
  | 'index'
  | 'name'

type BatchRenameOptions = {
  template: string
  startIndex: number
  padding: number
}

type BatchRenamePreviewItem = {
  relPath: string
  currentName: string
  nextName: string
  nextRelPath: string
  conflict: boolean
  reason: string
}

type BatchRenamePreviewResult = {
  items: BatchRenamePreviewItem[]
  validCount: number
  conflictCount: number
}
```

说明：

- 首版模板只负责生成文件名，不负责改目录结构
- `nextRelPath` 用于执行前检查最终目标路径

### 18.10 后端接口草案

主要文件：

- `desktop-source/app.go`

## 20. 正式任务五：目录健康中心

### 20.1 任务目标

把目前分散的清理、校验、缓存管理能力集中成一个统一入口，帮助用户维护长期使用后的图库健康状态。

### 20.2 适合解决的问题

- 数据目录长期使用后容易积累残留
- 用户不清楚缓存占用、失效引用、空目录情况
- 清理能力分散在多个入口，缺乏整体视图

### 20.3 建议范围

- 统一展示目录健康概览
- 检查空目录
- 检查无效标签引用
- 检查无效收藏引用
- 检查缓存占用
- 提供一键清理或修复入口

### 20.4 建议展示项

- 图片总数
- 缓存目录体积
- 空目录数量
- 失效标签引用数量
- 失效收藏引用数量

### 20.5 本次不做

- 磁盘级全盘扫描
- 外部目录健康修复
- 自动后台无限清理

### 20.6 验收标准

- 用户可以看到健康状态摘要
- 用户可以执行至少一项修复或清理动作
- 清理结果有明确反馈
- 不会误删受管图片

### 20.7 任务定位收敛

`目录健康中心` 的目标不是做全盘诊断工具，也不是做系统级清理器，而是把当前项目里已经存在但分散的缓存清理、空目录清理、失效引用校验能力统一到一个稳定入口。

首版目标收敛为：

1. 给用户一个统一的健康状态摘要
2. 统一提供常见治理动作入口
3. 让“可清理”和“可修复”的问题被看见
4. 不引入危险、不可解释的自动化清理

首版不追求：

- 全盘磁盘扫描
- 第三方目录修复
- 持续后台自动治理
- 复杂的历史趋势面板

### 20.8 当前基础与实现方向

当前项目已经具备：

- `ClearPreviewCache()`
- `CleanEmptyFolders()`
- `CleanupTags()`
- `measureDirectoryUsage(...)`
- `trash` 与 `image-meta-cache` 相关状态

这意味着：

- 健康中心不是从零开始
- 更合适的做法是“统一入口 + 健康摘要 + 统一动作封装”

正确实现方向应是：

- 后端聚合健康摘要
- 前端在设置中心统一展示
- 把零散动作收敛为可见、可解释的治理能力

#### 24.1.8 前端状态流草案

本节用于约束 `useImages.js` 的状态改造方向，避免实现时继续沿用“全量数组一路派生到底”的路径。

##### A. 当前状态流

当前链路大致为：

```text
fetchImages()
  -> images
  -> currentImages
  -> finalImages
  -> stackedImages
  -> paginatedImages
```

问题：

- `images` 是全量数组
- 搜索、标签、模型、LoRA、日期筛选全部建立在全量数组上
- 分页发生在所有派生计算之后

##### B. 目标状态流

建议拆成两条模式：

```text
标准模式：
fetchImages()
  -> images
  -> currentImages
  -> finalImages
  -> stackedImages
  -> paginatedImages

性能模式：
fetchImagesPage(query)
  -> pagedImages
  -> visibleImages
```

说明：

- 标准模式保留当前思路，减少一次性改动风险
- 性能模式下不再要求前端持有完整结果集

##### C. 建议新增状态

建议在 `useImages.js` 中新增：

```ts
performanceSettings
gallerySummary
directoryHealthSummary
galleryLoadMode
pagedImages
pagedTotal
pagedTotalPages
hasMorePagedImages
isPagedLoading
isPagedAppending
modeReason
```

职责建议：

- `performanceSettings`
  - 保存当前模式配置
- `gallerySummary`
  - 用于顶部状态条
- `directoryHealthSummary`
  - 用于设置中心健康区
- `galleryLoadMode`
  - 明确当前是 `standard` 还是 `performance`
- `pagedImages`
  - 仅性能模式下使用

##### D. 建议保留的状态

以下状态仍建议继续保留：

- `activeRoot`
- `activeSub`
- `activeChild`
- `searchQuery`
- `activeTagFilter`
- `activeModelFilter`
- `activeLoraFilter`
- `activeDatePreset`
- `activeDateStart`
- `activeDateEnd`
- `sortBy`
- `sortOrder`

原因：

- 这些状态已经是项目现有筛选语义
- 只需要把它们从“前端过滤条件”逐步转为“查询参数”

##### E. 性能模式下的计算原则

性能模式下建议遵守：

- 不对 `pagedImages` 再做全量语义上的本地搜索
- 不在前端重新计算完整目录树图片总量
- 不在每次分页结果变化时重建所有筛选统计
- 非必要不启用图片堆叠的全量聚合计算

首版建议：

- 性能模式下可以保留堆叠开关，但默认关闭
- 如保留堆叠，仅对当前页结果进行轻量处理

##### F. 建议新增方法

建议在 `useImages.js` 中新增：

```ts
loadPerformanceSettings()
savePerformanceSettings()
fetchGallerySummary()
fetchDirectoryHealthSummary()
fetchImagesPage()
loadNextImagesPage()
refreshCurrentGalleryView()
```

职责建议：

- `refreshCurrentGalleryView()`
  - 根据 `galleryLoadMode` 自动选择 `fetchImages` 或 `fetchImagesPage`

##### G. 建议调整的方法

以下现有方法建议调整：

- `fetchImages`
  - 只负责标准模式
- `setSortBy`
  - 触发 `refreshCurrentGalleryView`
- `setSortOrder`
  - 触发 `refreshCurrentGalleryView`
- `setPage`
  - 标准模式沿用当前逻辑
  - 性能模式直接触发 `fetchImagesPage`
- `setItemsPerPage`
  - 同时更新设置并刷新当前视图

##### H. 组件联动草案

建议组件职责如下：

- `SettingsCenterDialog.vue`
  - 加载 / 保存性能设置
  - 加载健康摘要
- `ImageGallery.vue`
  - 只消费 `currentImages` 或 `pagedImages` 暴露出的统一结果
  - 不自行判断模式策略
- `App.vue`
  - 初始化阶段加载性能设置
  - 在 `images:changed` 事件后调用统一刷新方法

##### I. 首版兼容原则

为控制风险，首版建议保留以下兼容策略：

- 标准模式完全兼容现有 `GetImages`
- 性能模式单独走 `GetImagesPage`
- 只有在确认性能模式稳定后，再考虑让标准模式也迁移到统一分页接口

这能避免一次性把现有图库主链路全改掉。

#### 24.1.10 事件触发时序草案

本节用于约束 `v2.2.0` 中设置变更、图片变化、健康动作执行后的刷新流程，减少重复刷新和状态错乱。

##### A. 应继续复用的现有事件

当前项目已经存在并正在使用：

- `images:changed`
- `auto-rules:progress`
- `shortcut:triggered`

`v2.2.0` 阶段不建议新增过多事件名称，优先复用 `images:changed` 完成图库刷新。

##### B. 应用启动时序

建议时序：

```text
App mounted
  -> loadPerformanceSettings()
  -> fetchGallerySummary()
  -> refreshCurrentGalleryView()
  -> fetchDirectoryHealthSummary() (可延后到设置中心首次打开时)
```

说明：

- 健康摘要不是首屏阻塞项
- 首次进入应用时应优先让图库可见

##### C. 设置修改时序

当用户在 `SettingsCenterDialog.vue` 修改性能模式设置时，建议：

```text
用户修改设置
  -> SaveGalleryPerformanceSettings(settings)
  -> 更新 performanceSettings
  -> fetchGallerySummary()
  -> refreshCurrentGalleryView()
```

说明：

- 设置保存成功后立即刷新当前图库视图
- 不需要等待用户关闭设置中心后再生效

##### D. 图片变化时序

当后端触发 `images:changed` 时，建议：

```text
EventsOn('images:changed')
  -> fetchGallerySummary()
  -> refreshCurrentGalleryView()
  -> Home / StatisticsDashboard 按需刷新轻量摘要
```

说明：

- `refreshCurrentGalleryView()` 内部自行判断走标准模式还是性能模式
- 避免每个组件分别直接重跑全量 `fetchImages`

##### E. 健康动作执行时序

当用户执行健康动作时，建议：

```text
RunDirectoryHealthAction(action)
  -> fetchDirectoryHealthSummary()
  -> fetchGallerySummary()
  -> 如动作影响图库内容，则 refreshCurrentGalleryView()
```

动作影响判断建议：

- `clear_preview_cache`
  - 不强制刷新图库内容
  - 只刷新健康摘要和图库摘要
- `clean_empty_folders`
  - 需要刷新图库视图
- `cleanup_tags`
  - 需要刷新图库视图与标签相关状态

##### F. 分页加载时序

性能模式下建议：

```text
进入图库
  -> fetchImagesPage(page=1)
点击下一页 / 改变页大小 / 改变排序 / 改变筛选
  -> fetchImagesPage(newQuery)
```

如果采用“加载更多”交互，则建议：

```text
初次加载
  -> fetchImagesPage(page=1)
点击加载更多
  -> loadNextImagesPage()
  -> 合并到 pagedImages
```

首版二选一即可：

- 分页式切页
- 加载更多

不要首版同时做两套主交互。

##### G. 组件职责边界

为减少重复刷新，建议：

- `App.vue`
  - 负责全局事件接收和统一刷新调度
- `useImages.js`
  - 负责图库数据刷新逻辑
- `Home.vue`
  - 只刷新首页摘要，不再自己决定图库读取策略
- `StatisticsDashboard.vue`
  - 只刷新统计摘要，不直接决定性能模式行为

##### H. 错误处理时序

建议统一处理：

```text
接口失败
  -> 保留上一份可用数据
  -> 显示 toast
  -> loading 状态正确结束
```

不建议：

- 失败后直接清空当前结果
- 失败后长时间停留在 loading
- 每个组件各自定义不一致的失败行为

##### I. 首版事件结论

`v2.2.0` 首版建议只在以下场景触发全局图库刷新：

- 性能设置变更后
- `images:changed`
- 健康动作执行且确实影响图库内容时
- 用户主动刷新当前视图时

这能把刷新行为控制在可解释的范围内。

#### 24.1.12 迁移与兼容策略草案

本节用于约束 `v2.2.0` 对现有 `settings.json`、缓存目录和旧接口路径的兼容方式，避免实现阶段出现重复迁移、缓存污染或升级后回退困难。

##### A. 总体原则

`v2.2.0` 的迁移策略应遵守：

- 复用现有 `Settings.PathVersion` 机制
- 不引入第二套独立版本号体系
- 新增字段必须向后兼容
- 旧用户升级后应直接可用，不要求手工清理数据
- 性能模式的引入不能破坏标准模式

##### B. `settings.json` 兼容策略

当前 `Settings` 已包含：

- `PathVersion`
- `TrashRetentionDays`
- `ShortcutSettings`
- `UserProfile`
- `UtilityMenu`

`v2.2.0` 建议在 `Settings` 中追加：

```go
GalleryPerformanceMode          string `json:"galleryPerformanceMode,omitempty"`
GalleryInitialBatchSize         int    `json:"galleryInitialBatchSize,omitempty"`
GalleryPageSize                 int    `json:"galleryPageSize,omitempty"`
GalleryThumbPreferred           bool   `json:"galleryThumbPreferred,omitempty"`
GalleryBackgroundVariantWarmup  bool   `json:"galleryBackgroundVariantWarmup,omitempty"`
GalleryMetadataLazy             bool   `json:"galleryMetadataLazy,omitempty"`
```

兼容要求：

- 老版本 `settings.json` 没有这些字段时，`loadSettings()` 自动补默认值
- 字段非法或缺失时，在 `loadSettings()` 中归一化
- 若归一化后值发生变化，沿用当前模式自动 `saveSettings(settings)`

建议默认值：

```json
{
  "galleryPerformanceMode": "auto",
  "galleryInitialBatchSize": 60,
  "galleryPageSize": 50,
  "galleryThumbPreferred": true,
  "galleryBackgroundVariantWarmup": true,
  "galleryMetadataLazy": true
}
```

##### C. `PathVersion` 使用建议

当前项目已经使用：

- `pathVersionRootRelative = 2`

`v2.2.0` 建议：

- 不为了新增设置字段单独提升 `PathVersion`
- 只有当“磁盘路径语义”或“持久化引用语义”发生变化时才提升

也就是说：

- 性能模式设置字段新增
- 健康摘要接口新增
- `GetImagesPage` 新接口新增

这些都不应触发 `PathVersion` 变化。

只有当未来出现以下情况时，才考虑升级 `PathVersion`：

- 缩略图或预览图存储路径结构发生变化
- 图片引用路径的持久化格式发生变化
- 批次、精选集、导出包等后续功能引入新的路径语义

##### D. `image-meta-cache.json` 兼容策略

当前缓存已包含：

- 基础文件信息
- `MetadataScanned`
- `HasMetadata`
- `HasWorkflow`
- `Positive / Negative`
- `Model / Sampler / Loras`
- `SearchText`

`v2.2.0` 建议：

- 不新增与分页强绑定的瞬时字段到 `image-meta-cache.json`
- 不把“当前页结果”写入缓存文件
- 继续把它定位为“单图元数据缓存”

可以接受的扩展：

- 补充缩略图是否已生成的轻量标记
- 补充预览图是否已生成的轻量标记

不建议首版加入：

- 分页结果缓存
- 查询结果缓存
- UI 状态缓存

原因：

- 这类缓存失效策略复杂
- 会增加调试成本
- 首版收益不够稳定

##### E. `image-variants` 目录兼容策略

当前目录：

- `data/image-variants/thumb`
- `data/image-variants/preview`

`v2.2.0` 建议保持目录不变，不迁移历史缓存目录结构。

兼容要求：

- 程序启动或首次使用时确保目录存在
- 缓存缺失时自动补生成，不要求预迁移
- `ClearPreviewCache()` 仍然可清空整个 `image-variants`
- 清空后目录自动重建

首版不建议：

- 改变 `thumb / preview` 路径层级
- 引入第三种变体目录
- 对旧缓存执行复杂批量迁移

##### F. 标准模式与性能模式兼容策略

`v2.2.0` 的关键兼容要求：

- 标准模式继续使用现有 `GetImages(sortBy, sortOrder)`
- 性能模式新增 `GetImagesPage(query)`
- 前端通过 `galleryLoadMode` 在两条链路间切换

回退要求：

- 如果 `GetImagesPage` 失败，性能模式不应破坏标准模式
- 必要时允许用户切回标准模式继续使用
- 不要因为性能模式接口失败而清空现有图库数据

##### G. 目录健康中心兼容策略

目录健康中心是“统一入口”，不是“全新底层系统”。

首版应复用现有能力：

- `ClearPreviewCache()`
- `CleanEmptyFolders()`
- `CleanupTags()`

兼容要求：

- 即使健康中心未完成，原有独立能力也不应被删除
- 迁移完成后，原有能力可变为健康中心内部动作，不要求立刻移除旧代码路径

建议顺序：

1. 先新增 `GetDirectoryHealthSummary()`
2. 再新增 `RunDirectoryHealthAction(action)`
3. 最后再决定是否将旧入口完全隐藏

##### H. 升级与回退策略

首版必须支持以下场景：

- 老用户升级到 `v2.2.0` 后直接打开图库
- 用户清空缓存后重新进入图库
- 用户把模式从 `performance` 切回 `standard`
- 新接口异常时仍能保留上一份可用结果

不保证的场景可以明确为：

- 回退到老版本后二进制完全识别新设置字段

原因：

- 老版本通常会忽略未知字段，但不应为“回退老版本”过度设计新字段兼容逻辑

##### I. 启动时迁移顺序建议

应用启动时，建议顺序如下：

```text
loadSettings()
  -> 归一化新性能字段
  -> 如有必要自动 saveSettings()
  -> 确保 trash / image-variants 目录存在
  -> 启动时不主动批量重建 thumb / preview
  -> 首次进入图库时再按需生成
```

说明：

- 不要在启动阶段做重型缓存重建
- 否则会抵消性能模式带来的收益

##### J. 调试与日志建议

为便于首版排查，建议在后端日志中明确记录：

- 当前性能模式设置值
- `GetImagesPage` 查询参数摘要
- 当前是否命中性能模式
- 健康动作执行结果摘要

但不建议：

- 日志输出完整图片列表
- 日志输出超长 Prompt 文本
- 日志输出大量重复缓存命中明细

##### K. 迁移结论

`v2.2.0` 的迁移策略应明确为：

- 新增设置字段，沿用 `loadSettings()` 归一化
- 不强制提升 `PathVersion`
- 不重构 `image-meta-cache.json` 的职责
- 不迁移 `image-variants` 目录结构
- 保持标准模式完整可用
- 性能模式作为增量能力接入，而不是替换全部旧链路

### 24.2 v2.2.1

- 完整导出预设

### 24.4 不建议的拆分方式

不建议这样拆：

- 把 `7` 个任务平均拆成三个版本
- 只按开发工作量拆，不按依赖关系拆
- 把 `模型 / LoRA 资产档案` 放在性能模式之前
- 把 `精选集 / 展示板` 放在批次管理之前强行上线

原因：

- 那样排期看似平均，但工程顺序不合理
- 会增加返工和回归成本

---

### 24.5 总体发布顺序结论

建议最终顺序如下：

1. `v2.2.0`
   - 大型图库性能模式
   - 目录健康中心
2. `v2.2.1`
   - 创作批次管理
   - 导出包助手
   - 批量重命名与命名规则
3. `v2.3.0`
   - 模型 / LoRA 资产档案
   - 精选集 / 展示板

这个拆分方式的优点：

- 先稳底盘
- 再补工作流
- 最后做产品深化
